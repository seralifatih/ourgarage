# Privacy nutrition label — App Store Connect answer key

Literal, top-to-bottom answers for the App Privacy questionnaire, generated by
auditing `pubspec.yaml`, the full transitive dependency tree
(`flutter pub deps`), every service file that talks to a network, and the
Info.plist. Cross-checked against RevenueCat's and Supabase's own published
data-collection disclosures — not assumed. Sources are cited inline.

**Previously flagged bug, now fixed.** An earlier audit of this document found
that RevenueCat was never given a Supabase-matched `appUserID`, which broke
the webhook and meant Purchase History could not be answered "linked to
identity." `lib/services/revenuecat_identity_sync.dart` now closes that gap —
see the writeup below — so Row 25 is answered as **Yes, linked** throughout
this document.

## Fixed: RevenueCat customer identity now follows the Supabase user

`PurchaseService.configure()` used to leave `PurchasesConfiguration.appUserID`
at its default `null`, and nothing ever called `Purchases.logIn()`. RevenueCat
tracked every user under its own anonymous, device-generated ID instead of the
Supabase user ID, which broke two things: the webhook could never match a
purchase to a household, and Purchase History could not be marked "linked to
identity."

**Fix, in `lib/services/revenuecat_identity_sync.dart`:** a `keepAlive`
Riverpod provider listens to `currentUserIdProvider` (the Supabase auth
stream) with `fireImmediately: true`, and calls
`PurchaseService.identify(userId)` — which wraps `Purchases.logIn(userId)` —
on every sign-in, including a session already restored at app launch before
any live sign-in event fires. `PurchaseService.resetIdentity()` — wrapping
`Purchases.logOut()` — runs on sign-out, so a shared/handed-down device
doesn't keep attributing purchase history to the previous user.

The anonymous-purchase edge case this task specifically had to trace: a
free-tier-only lifetime purchase made **before** the user ever signs in is not
orphaned. RevenueCat's documented merge behavior (`Identifying Customers`)
aliases the pre-login anonymous customer onto `userId` the first time that ID
is ever logged in, carrying the entitlement across — verified in
`test/services/purchase_service_test.dart` (`'a free-tier-only lifetime
purchase made before sign-in is not orphaned — identify merges it in'`), not
just assumed from the docs. A *second* device or reinstall starts its own new
anonymous RevenueCat customer and does not inherit the first device's
history — restorePurchases (already wired to Settings/paywall) is what
surfaces the entitlement there, exactly as it did before this fix.

Covered by tests:
- `test/services/purchase_service_test.dart` — the `identify`/`resetIdentity`
  API in isolation, including the merge/no-merge cases and SDK-failure
  handling.
- `test/services/revenuecat_identity_sync_test.dart` — the Riverpod bridge
  end to end, including the boot-time "session already restored, no live
  sign-in event" case the `fireImmediately: true` fix exists for.

**Not (and cannot be) covered by an automated test:** whether RevenueCat's
*server* actually puts the Supabase user ID in the `app_user_id` field of a
real webhook POST to `supabase/functions/revenuecat-webhook/index.ts` — that
leg is RevenueCat's backend talking to Supabase's, entirely outside this
Flutter codebase. Verify manually before trusting the webhook in production:

1. In RevenueCat's dashboard, make a **sandbox** purchase while signed in to
   Supabase (`Purchases.logIn` should already have run — confirm via
   RevenueCat's Customers list that the sandbox purchase is attached to a
   customer ID matching the Supabase `auth.users.id`, not an anonymous
   `$RCAnonymousID:...` one).
2. In the RevenueCat dashboard's **Webhooks** log (Project settings →
   Integrations → Webhooks → the Supabase endpoint), open the delivered event
   for that purchase and confirm its JSON body's `event.app_user_id` equals
   that same Supabase user ID.
3. In the Supabase project's Edge Function logs for `revenuecat-webhook`,
   confirm the function found a `household_members` row for that user id (not
   the `no-household` warning path) and actually granted premium.

## Question 1 — "Do you or your third-party partners collect data from this app?"

**Answer: Yes.**

Tempting to answer No, since a free/local-only user's data never leaves the
device. But the question is scoped to the whole binary across all its
features, and household sharing — reachable from Settings by any user —
uploads user content and collects an Apple ID email via Supabase. Answering No
here and shipping the sharing feature as-is would be a misrepresentation, and
it's the specific kind of mismatch Apple's review checks for.

### Row-by-row detail

**Row 1 — Name.** From Sign in with Apple (`AppleCredential.givenName` /
`.familyName` in `auth_service.dart`), sent to the app only on the very first
authorization between the user and the app; every later sign-in returns null.
Stored to name the household ("Fatih's garage"); if withheld, the household
is called "My household" and nothing else changes. Only collected once the
user taps "Share with household" or "Join a household" — never on launch.

**Row 2 — Email Address.** Also from Sign in with Apple, same trigger point.
If the user chooses Hide My Email, the app receives Apple's private relay
address and never sees the real one — confirmed this is Apple's own
first-party behavior, not something this app's code affects either way.

**Row 20 — Other User Content.** Vehicles, service records, reminder rules,
odometer readings, costs, and notes — confirmed by reading
`remote_garage.dart`'s `upsertVehicles`/`upsertServiceRecords`/
`upsertReminderRules`, which are only ever called from the household-migration
and sync code paths, never on first launch or for a local-only user.

**Row 23 — User ID.** The Supabase auth user ID (`auth.currentUser?.id`),
used to identify the account and to resolve household membership
(`getHouseholdId` in `auth_service.dart`). This is collected independently of
the RevenueCat identity sync below — it's a Supabase-native identifier, not
the RevenueCat one.

**Row 25 — Purchase History.**

- Linked to identity = **Yes**. `lib/services/revenuecat_identity_sync.dart`
  calls `Purchases.logIn(userId)` with the Supabase user ID on sign-in (see
  "Fixed: RevenueCat customer identity now follows the Supabase user" above),
  so purchases resolve to the same Supabase user ID as row 23, not an
  anonymous RevenueCat ID.
- **Used for tracking = No** — RevenueCat's collection of purchase history is
  not used to track users across other companies' apps or websites, and this
  app integrates no advertising or cross-app attribution SDK that would
  change that.
- Collected only via `PurchaseService.purchasePackage` / `.restorePurchases`
  (`purchase_service.dart`), which are only reachable from the paywall and
  Settings — never automatically.

**All other rows are No** — confirmed by the dependency audit above (no SDK
capable of collecting them exists in the binary) and by reading every file
under `lib/` that makes a network call (`auth_service.dart`,
`remote_garage.dart`, `purchase_service.dart` — nothing else does).

## Question 3 — "Does this app use data to track users?"

**Answer: No.**

- Nothing collected here is shared with data brokers or third-party
  advertisers for cross-app/cross-site tracking.
- No advertising identifier (IDFA) is read anywhere in the codebase — grepped
  for `IDFA`, `advertisingIdentifier`, `AdSupport` across `lib/` and the iOS
  project: zero matches.
- **`ios/Runner/Info.plist` contains no `NSUserTrackingUsageDescription` key**
  (checked directly) — confirming no ATT prompt exists, which is only correct
  because nothing in the app requires one. If this key or an ATT call is ever
  added later without a real tracking use case, it becomes its own rejection
  risk (prompting for a permission the app doesn't use).
- RevenueCat's purchase-history collection does not itself constitute
  cross-app tracking per RevenueCat's own guidance, and this app adds no
  attribution SDK (AppsFlyer, Adjust, Facebook SDK, etc.) that would.

## Third-party SDK disclosures, checked against their own documentation

Per your request to verify rather than assume — here is what each vendor's
own current disclosure says, with sources.

**RevenueCat** (`purchases_flutter`): RevenueCat's own Apple App Privacy page
states they collect **Purchase History** as the sole data type their SDK
reports by default, and explicitly: *"the default Privacy Manifest only
reflects what the SDK will collect out of the box... RevenueCat will not link
purchase history to a user unless custom IDs or device identifiers are being
used, which need to be implemented on the developer side."* That is the exact
condition this app is currently in (custom ID not implemented — see the bug
above), and it's also RevenueCat's own confirmation that nothing beyond
Purchase History is collected by their SDK as integrated here — no location,
no contacts, no advertising identifiers, since this app uses none of
RevenueCat's optional integrations that would add those.

**Supabase** (`supabase_flutter`): Supabase acts as a data **processor**, not
an independent collector — it stores and serves back exactly what this app's
own code sends it (auth email/name via `gotrue`, garage rows via
`postgrest`), governed by Supabase's Data Processing Addendum. Supabase does
not itself inject additional data collection into the client SDK beyond what
the app explicitly writes — confirmed by reading every Supabase call site in
this codebase (`auth_service.dart`, `remote_garage.dart`); there is no
Supabase Analytics, no Realtime subscription, no Storage upload anywhere in
`lib/`. This matches Supabase's own description of their role as a processor
acting under this app's instructions, not an independent data collector in
its own right.

## The free-tier framing, for context while filling the form

A user who never taps "Share with household" or "Join a household" is never
asked to sign in and has zero data collected — the entire local database
stays on-device. The ASC questionnaire has no way to express "collects
nothing unless the user opts into one specific feature," so every "Yes" above
necessarily overstates what most users will actually experience. `privacy.md`
and the App Store description both state this explicitly so it isn't lost in
translation to the nutrition-label format.
